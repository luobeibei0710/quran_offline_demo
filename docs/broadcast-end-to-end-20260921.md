# 广播链路端到端验证（2026-09-21，全经音频）

用**真实全经诵读音频**在主机上跑完整链路：音频 → 离线转写 → 全经匹配 → 权威译本。
与真机走的是同一套代码（同一个 `BroadcastTranscriber`、`QuranMatchService`、
`JsonVerseTranslationRepository`），没有简化实现。

## 1. 测试设置

| 项 | 值 |
|---|---|
| 音频源 | `https://server8.mp3quran.net/afs/{001..114}.mp3`（Mishary Rashid Alafasy 全经整章） |
| 语料 | 全经 6236 节（Tanzil 快照 + 本仓库生成的 token 表，maxSpan=8） |
| 译本 | 62 种语言（QuranEnc 授权），本次核对中文马坚与英文 Saheeh |
| 窗口 | 30 秒，每章均匀采样 3 个（避开开头求护词与结尾静音） |
| 推理 | 主机 ONNX Runtime 1.22.0（`host_ort_server.py`，仅 127.0.0.1） |
| 判据 | 音频来自已知章，**匹配结果是否落在该章内**是唯一可用的 ground truth，且不参与匹配决策 |

测试章节覆盖不同长度与结构：开端章（52 s / 7 节）、雅辛章（876 s / 83 节）、
至仁主章（679 s / 78 节，含 31 次重复节）、王权章（455 s / 30 节）、
纯洁章（22 s / 4 节，短于一个窗口）。

### 独立核对：节号是否算对

音频按节均匀推进，可以用「窗口中心时间 ÷ 每节平均时长」独立推算期望节号，
再与匹配结果比较（王权章 455 s / 30 节 = 15.2 s/节）：

| 窗口中心 | 推算节号 | 匹配结果 | 结论 |
|---|---|---|---|
| 121.4 s | ≈ 8.0 | `67:8–9` | 吻合 |
| 227.7 s | ≈ 15.0 | `67:15–17` | 吻合 |
| 334.1 s | ≈ 22.0 | `67:22–23` | 吻合 |

三次都落在推算位置，说明匹配不只是「章对了」，节位也对。

## 3. 本轮暴露并修复的三个缺陷

这一轮的价值主要在这里：**端到端跑真实音频才能暴露的问题，单元测试看不出来。**

### 3.1 匹配跨度不足（`maxSpan`）

**现象**：开端章窗口转写实际覆盖 6 节（`1:1–1:6`），匹配只给 4 节，
解释比例被压到 0.60。

**根因**：`maxSpan = 4`。之前的标定是在**王权章**上做的（30 秒 ≈ 2 节），
没暴露这个问题；全经里有大量极短节（开端章 2–9 词/节、多福章等），
30 秒可跨 5–6 节。

**处置**：token 表重新生成（maxSpan 4→8，46,752 条跨度 / 45 MB），
`BroadcastMatchConfig.maxSpan` 同步取 8。

### 3.2 候选池按 CTC 分数截断，长跨度候选被整体排除

**现象**：即使把 `maxSpan` 提到 8 仍无改善。

**根因**（诊断脚本 `tool/diagnose_match_test.dart` 给出决定性数据）：
候选池按 CTC 排序分取前 N 个，而按帧归一化的分数**系统性偏好极短候选**：

```
champion: 1:3-3（仅 2 个 token）         score 0.330
正确的 1:3-7（49 个 token）              排名在 130 名开外
```

**处置**：`runnerUpLimit` 放大到 1024（即不截断），并在裁决前按
「**参考词数与转写词数的接近度**」重排候选，只对前 192 个做词级对齐 ——
既让长跨度候选进入裁决，又把成本压回可用范围。

### 3.3 分段证据不足以支撑跨节候选（根本原因）

**现象**：上面两处修完后，`1:3–1:7` 仍然选不出来。

**根因**：`CtcScorer` 要求候选满足 `token 数 × 2 + 1 ≤ 帧数`。转写按声学停顿
把 30 秒窗口切成 3–10 秒的子窗（为了 ASR 准确），而匹配是**逐子窗**做的 ——
子窗帧数只够短候选，49 token 的正确跨度被判「不可行」直接跳过。

**处置**：转写仍分段（保 ASR 质量），但**匹配改用整段音频的原生证据**
（`BroadcastFragment.matchEvidence`：单段时复用，多段时对整段再跑一次前向）。
这一次推理不服务转写，只为给匹配提供足够的帧数。

## 4. 耗时（主机 x86，真机需另行测量）

| 阶段 | 值 |
|---|---|
| 转写（分段，含 30 秒音频切分） | 0.9–1.7 s（命中缓存时 30–100 ms） |
| 匹配（召回 + CTC 精排 + 裁决 + 词级对齐） | 0.26–1.36 s |
| 译本查表 | 微秒级（首次加载该语言约 1 s，之后命中内存） |

**注意**：匹配耗时是真机上会被放大的环节（设备算力约为主机的 1/3–1/2），
按 1.4 s 估算真机可能到 3–5 s。对 30 秒片段的**终稿**处理可以接受，
但**预览**（1 秒周期）需要降配（`topK`/`maxSpan` 减半），这一点尚未在真机验证。

## 5. 明确没有验证的部分

1. **真机未验证**：以上全部是主机推理。真机的算力、麦克风拾音、断句时机都可能
   显著改变结果，尤其 §4 的耗时。
2. **节号正确性只有 3 个窗口做过独立核对**（王权章），其余只验证到「章正确」。
3. **译本文本未人工抽检**：只确认了「查到了对应译本」与来源标记正确，
   没有逐句核对译文语义。
4. **至仁主章的 31 次重复节**没有专门设计用例验证歧义行为（本轮三次窗口都落在
   唯一节上）。
5. **61 种非中英语言的译本未在端到端中验证**（测试只取中文与英文）。
