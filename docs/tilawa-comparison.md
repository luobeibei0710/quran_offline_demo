# 与 Tilawa 原项目的实测对比（同一批语料 / 同一套指标）

> 目的：把 `assets/quran_offline/corpus/` 里的三段多节语料**同时**喂给「Tilawa 官方 npm 包」与
> 「本项目」，用**同一套指标代码**（本项目的 `WordAlignment`）算出覆盖率 / 准确率 / F1 与章节命中，
> 看清两边各自强在哪、弱在哪。结论不是一边倒 —— 见下表与「怎么读这张表」。

## 方法（保证可比）

| 维度 | 做法 |
|------|------|
| 音频 | 同一批 WAV：`assets/quran_offline/corpus/*.wav`（16 kHz / 单声道 / 16-bit，`download_corpus.sh` 生成） |
| 文本资产 | 同一份：`vocab.json` / `quran_ctc_tokens.json` / `quran.json`，都来自 Tilawa v0.2.0 官方发布包 |
| 模型 | 同一个：`fastconformer_full_mixed_ort122.onnx`（本项目改造版，57 个 `ConvInteger` → `DequantizeLinear + Conv`，与原模型逐帧 argmax 一致率 100%），这样 Node 侧 ORT 1.22 也能加载 |
| Tilawa 侧配置 | **完全默认**（`BALANCED_STREAMING_CONFIG`，`audioChunkMs=150`、discovery 触发 2 s / tracking 0.25 s、窗口 30 s / 12 s），不做调参 |
| 本项目侧配置 | **完全默认**（`triggerSeconds=0.75`、窗口 1.2~15 s、`spanPenalty=0.1` 等），同样不调参 |
| 转写稿口径 | 两侧一致：识别到的章节 → 展开成节 → 按「新覆盖到的节」累加 → 取这些节的标准经文词序列 |
| 原文口径 | 两侧一致：期望区间的标准经文，并提供「去掉太斯米前缀」变体，取 F1 更高者 |
| 指标 | 两侧都由本项目 `WordAlignment` 计算（阈值/近似词半分口径一致）：覆盖率 =(一致+0.5×近似)/原文词数、准确率 =同式/转写词数、F1 取调和平均 |

复现命令：

```bash
# Tilawa 侧（Node）
cd tools/tilawa_compare && npm install
OUT=/tmp/tilawa_bench.json node run_bench.mjs

# 本项目侧：真机跑批（--dart-define=quran_auto_corpus=true），从日志取「稳定命中」序列
# 统一口径对比（两侧都用本项目的指标实现）
dart run tool/tilawa_compare_metrics.dart /tmp/tilawa_bench.json /tmp/ours_bench.json
```

## 结果

| 语料（时长） | 实现 | 章节命中 | 一致 | 近似 | 缺失 | 多余 | 覆盖率 | 准确率 | F1 | 结论 | 处理耗时 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `36:1-5`（28 s） | **Tilawa** | 5/5 | 16 | 0 | 0 | 0 | 1.000 | 1.000 | **1.000** | 优秀 | 8.3 s |
| `36:1-5`（28 s） | 本项目 | 5/5 | 16 | 0 | 0 | 11 | 1.000 | 0.593 | 0.744 | 一般 | 41.7 s |
| `55:1-13`（87 s） | Tilawa | **0/13** | 2 | 3 | 35 | 0 | 0.074 | 0.292 | **0.119** | 较差 | 120.6 s |
| `55:1-13`（87 s） | **本项目** | 13/13 | 43 | 1 | 2 | 9 | 0.926 | 0.806 | **0.861** | 良好 | 151.5 s |
| `67:1-11`（159 s） | **Tilawa** | 11/11 | 126 | 0 | 0 | 70 | 1.000 | 0.643 | **0.783** | 良好 | 182.2 s |
| `67:1-11`（159 s） | 本项目 | 7/11 | 126 | 0 | 0 | 83 | 1.000 | 0.603 | 0.752 | 良好 | 430.7 s |

口径说明：

- 两侧的「章节命中」都按各自**输出的章节序列**统计：Tilawa 用其 `verse_match` 事件（它内部判定稳定后的输出），
  本项目用识别序列（含瞬时冠军，已是较宽松的口径）；
- 本项目一栏里 `55:1-13`/`67:1-11` 的一致词数来自真机应用日志的实测值（同一份 `WordAlignment` 计算），
  `36:1-5`/`55:1-13` 的章节命中另由 `tool/tilawa_compare_metrics.dart` 复算校验；
- 平台不同：Tilawa 跑在 Mac（x86 / Node + onnxruntime-node），本项目跑在真机（Redmi 24117RK2CC / arm64）。
  此前实测过两端数值差异对判定影响很小（同一批官方样本两端结论一致），但严格同机对比未做。

## 怎么读这张表

**Tilawa 更强的地方**

- 短句连读（`36:1-5`）：5 节全中、**零多余**、F1 = 1.000。它的联合匹配 + 片段/前缀那套
  （`JOINT_FRAGMENT_BLEND`、`JOINT_PREFIX_*`）在「音频就是这几节」时几乎不出错；
- 长段连续诵读（`67:1-11`）：11 节全中且顺序正确（甚至继续往前识别到 67:18），
  说明它的跟踪器能顺着「下一节」推进；本项目在同一段上只单独命中 7/11（其余靠跨度/其它候选覆盖到词）；
- **快**：同样三条语料，Tilawa 8/121/182 s，本项目 42/152/431 s（本项目的窗口更密、窗口更长，
  单次推理更贵；这条是延迟/CPU 的真实差距）。

**本项目更强的地方**

- `55:1-13`：Tilawa **锁错了章**——音频开头「الرحمن علم القرآن…」被它的文本联合匹配拉到了
  `1:3`（法谛海哈），随后它的「下一节」推进逻辑沿着 `1:4 → 1:5 → 1:6` 一路错下去，
  整段 87 s 没有恢复；章节命中 0/13、覆盖率 0.074。本项目这一段是 13/13、覆盖率 0.926。
  值得注意的是它的一发式 `transcribe()` 在同一段上返回 `0:0`（分数低于 0.8 的信任阈值），
  说明它内部也知道不可信，但流式侧仍然把 `1:3~1:6` 以 0.82~1.00 的置信度报了出来；
- 残余误差的形态不同：本项目的误差是「多余词」（短窗口上把片段认成别的短句，如 `2:1`「الم」、
  `1:3`「الرحمن الرحيم」），不会像 Tilawa 那样整段锁错章；`55:1-13` 这种「连读多节、含常见短语」
  的语料上这个差异是决定性的。

**两边共同的弱点（同一类根因）**

- **推进/延续逻辑会把一次误匹配放大成持续错误**：Tilawa 在 `55:1-13` 上错章后一路沿「下一节」
  推进；本项目此前也在真机上把 159 s 语料裁掉了 155 s（错误匹配也触发窗口推进）。
  本项目已加闸（只在冠军是「已确认序列的延续」时推进 + 单次最多裁 60%），Tilawa 侧无此闸。

## 接下来最值得做的事

1. 把本项目的**片段/前缀匹配**补上（直接对应「多余词」那条误差）；
2. 借鉴 Tilawa 的两点：**联合文本打分**（`bestJoint03Match`，用文本相似度稳住章号）与
   **信任阈值门控**（分数不够就不上报，而不是报高置信度）；
3. 借鉴它更省的窗口策略（discovery 阶段 2 s 触发 / 30 s 窗口，tracking 阶段 0.25 s / 12 s 窗口），
   本项目的固定 0.75 s 触发 + 15 s 窗口在长语料上 CPU 明显更贵。
