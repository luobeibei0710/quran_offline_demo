# 负结果记录：片段候选 + 内容帧短缺惩罚 + 序列先验，为何被回滚

> 目标：把语料验证里的「多余词」压下来（逐词 F1 从 0.74~0.86 往 0.95 推）。做法是给匹配器补
> **片段候选**（词边界上的前缀/中段）、按「候选解释了多少**内容帧**」加**短缺惩罚**、再加
> **信任门控**与**序列先验**（诵读按顺序进行）。
> 结论：**四处改动在真机上净负收益，已全部回滚**；本文记录数据与原因，避免重复踩。

## 1. 改了什么

| # | 改动 | 意图 |
|---|------|------|
| A | 片段候选：对前 3 个召回候选，在词边界上生成前缀 `[0, ½)`、中段 `[¼, end)`、`[½, end)` 三种 token 子序列参与打分 | 让「窗口只覆盖长节一部分」的音频能归属到该长节，而不是落到恰好能塞进窗口的短句上 |
| B | 短缺惩罚：`sortScore = 声学(每帧) + 跨度惩罚 + 2.0 × (1 − 解释的内容帧比例)` | 抵消「短候选只占少数帧、其余按空白算」带来的偏好（多报的机制） |
| C | 信任门控：`VerseMatchResult.trusted = 解释比例 ≥ 0.3`，语料验证的转写稿只采纳「稳定 + 可信」 | 挡掉解释不了窗口内容的候选 |
| D | 序列先验：冠军不是「上一节（稳定/已确认）的延续」时，把排序分差在 0.3 以内的延续候选提升为冠军（后来又加了「只在冠军本身较弱时生效」的条件） | 解决**文本歧义**：音频里的 «الرحمن الرحيم» 既是 `1:3` 的真实内容，也出现在 `55:1-2` 里 |

## 2. 真机实测（三段语料，同一台设备与同一条灌音链路）

基线 = 回滚后的当前实现（`02e66f4` 状态）；「多余/缺失」是逐词比对里的词数。

| 配置 | `36:1-5`（原文 16 词） | `55:1-13`（原文 47 词） | `67:1-11`（原文 126 词） |
|------|------------------------|-------------------------|--------------------------|
| **基线**（仅每帧归一化 + 跨度惩罚） | 覆盖 **1.000**、F1 **0.744**（多余 11） | 覆盖 **0.926**、F1 **0.861**（多余 9） | 覆盖 **1.000**、F1 **0.752**（多余 83） |
| A+B+C（片段 + 短缺 + 门控） | 覆盖 1.000、F1 0.711（多余 13） | — | — |
| A+B+C+D（先验无附加条件） | 覆盖 1.000、F1 **0.865**（多余 5）✓ | 覆盖 0.691、F1 **0.520** ✗（多余 31、稳定命中 20 节） | 覆盖 0.984、F1 0.586 ✗（多余 171、稳定命中 32 节） |
| A+B+C+D′（先验加「冠军较弱」条件） | 覆盖 1.000、F1 **0.711**（多余 13）✗ | 覆盖 **0.649**、F1 **0.678**（缺失 13 词）✗ | 覆盖 0.952、F1 0.772（多余 59，比基线少 24）但**稳定命中 20 节、章节命中 21/29**（基线 25/29）✗ |

信任门控在三次运行里分别丢弃 **0 / 0 / 3 / 1** 次 → 基本没起作用。
同一轮批量汇总：**章节命中 21/29 节、整段全中 1/3 条**（基线为 25/29 与 2/3）——即「多余词」略有下降，但**多报进来的错误章节把覆盖率与章节命中一起拉低**，整体更差。

## 3. 原因分析

1. **「解释内容帧比例」没有抓住真正的多报**：多报的候选（如 `1:3`）在**它自己的窗口**里
   解释比例往往很高 —— 因为那段音频**确实就是** `الرحمن الرحيم`。问题出在**文本歧义**（同一段音频
   对应多节经文），不是「候选解释不了音频」。实测门控丢弃 0~3 次可证。
2. **片段候选在真实音频上反而抢了正确候选的冠军**：合成证据里「完整候选声学近乎完美」，
   真实音频不是 —— 片段候选把 token 放在概率最高的少数帧、其余按空白摊掉，**每帧平均**因此可能
   低于正确但更长的完整候选；`55:1-13` 的覆盖率从 0.926 掉到 0.649（缺失 13 词）正是这么来的。
   短缺惩罚（2.0）不足以抵消这个真实存在的声学优势。
3. **序列先验会放大一次误匹配**：无条件先验把 `55:1-13` 从 0.861 拉到 0.520（覆盖率 0.691、
   稳定命中 20 节）—— 与 Tilawa 在 `55:1-13` 上「锁错章后沿下一节一路错下去」是**同一种失效**。
   加上「只在冠军较弱时生效」后虽然不再放大，但也**不再起作用**（弱冠军在真实音频里很少见）。
4. 结论：**per-window 的启发式（解释比例、片段、门控）解决不了跨窗口的歧义问题**。

## 4. 回滚与保留

- 回滚：`quran_matcher.dart`、`quran_recognizer.dart`（先验与容忍度）、`corpus_runner.dart`（可信要求）、
  `corpus_verify_page.dart`（日志措辞）、片段夹具与片段测试；
- 工作区与已验证状态一致（`flutter analyze` 无告警、127 用例全绿）；
- 保留：窗口推进的「延续闸门」（`isContinuation` + 单次最多裁 60%）—— 那条是**限制破坏性操作**，
  与本文这些**改变排序**的改动性质不同，且已在真机验证过（159 s 语料的前移量 155 s → 18.9 s）。

## 5. 下一步该怎么做（基于本轮证据）

1. **跨窗口的位置估计**，而不是单窗口重排：会话维护「当前在第几节第几词」，候选按**与该位置的
   关系**打分（Tilawa 的 tracker 就是这个思路：`transitionScore`、假设路径、`advancePrefixTokens`）。
   这是解决「长节片段归属」与「文本歧义」的共同钥匙，但属于**跟踪器级别**的重构；
2. **联合文本打分**（Tilawa 的 `bestJoint03Match`）：用文本相似度稳住章号，比 per-window 的
   声学重排更抗歧义；
3. **先做可验证的收口**：把「多报」这一层单独量化（本例已有：多余词 9~83），并给多报设定
   可接受上限（例如「多余词 ≤ 原文词数的 10%」）作为验收线，再谈改法；
4. 记住本轮的教训：**任何改变候选排序的改动，都必须用真机语料跑批验证**（合成证据会系统性
   高估它的收益）。
