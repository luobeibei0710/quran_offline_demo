# 旧 Demo 与流式链路

`lib/quran_offline/` 是本项目的早期 Demo，现在是**开发诊断入口**，不再是产品首页。
它承载三类回归能力，仍可正常使用；产品功能见 [README](../README.md) 与
[架构与数据流](architecture.md)。

保留它的理由很实际：广播侧的断句、匹配、对齐、指标都建立在同一套纯 Dart 算法上，
流式链路是**唯一能在设备上直接观察这些算法逐窗行为**的地方。

## 1. 入口

| 入口 | 位置 |
|------|------|
| 开发诊断 | 广播首页右上角**扳手图标**（tooltip 写明「开发诊断（旧 Demo）」） |
| 引导页兜底 | `BroadcastBootstrapPage` 初始化失败时页面底部「进入开发诊断（旧 Demo）」 |

启动后自动加载旧经文库（6236 节 + 词表 + span 表）与 ASR 模型（124.6 MB），
加载完成后跑一遍**内置样本自测**：逐条读取 `sample_*.wav` 走完整链路，
日志输出「期望 vs 实际 / 命中与否 / 召回数 / 耗时」，末尾汇总命中率。

| 内置样本 | 期望 |
|----------|------|
| `sample_001001.wav` | `1:1` |
| `sample_001002.wav` | `1:2` |
| `sample_002255.wav` | `2:255` |
| `sample_036001.wav` | `36:1` |
| `sample_112001.wav` | `112:1` |

（文件名即标准答案：`SSSAAA` = 章号 + 节号。）

> 广播首页**不执行**内置样本自测，避免占用推理资源并污染历史。

## 2. 界面与三个入口

主界面是「指标置顶 + 主区经文」布局：

| 区域 | 内容 |
|------|------|
| 状态条 | 当前阶段文案、输入电平条、稳定命中次数 |
| 章节栏 | 「已锁定」徽标、章名与 `surah:ayah`，其下一行汇总指标（置信度、声学分、词进度、窗口时长） |
| 主区 | 默认整句奥斯曼体经文（26 px、RTL、长节可纵向滚动）；开关打开时切为逐词提词器 |
| 日志条 | 固定在底部 76 px，显示最近 5 条事件，同时输出到 logcat |

AppBar 三个入口：

1. **语料验证**（`library_music`）——默认离线实际 ASR 校核，可切旧流式诊断（见 §3）；
2. **比对结果**（`compare_arrows`）——本轮转写 vs 原文的逐词对照页；
3. **重置**（`refresh`）——清空本轮状态。

页面底部按钮按状态切换：加载模型 / 开始识别 / 停止识别。

## 3. 三条链路的分工

| | 实时（主界面） | 离线校核（默认） | 流式诊断（Switch 关闭） |
|---|---|---|---|
| 输入 | 麦克风 | 语料 WAV | 同一语料 WAV，按实时节奏灌入 |
| 关注点 | 收音、延迟、实时章节与进度 | 模型实际转写的准确度 | 章节匹配、稳定事件与窗口推进 |
| 输出 | 实时章节与转写 | 实际 ASR 词、容错 F1/P/R、严格 WER | 章节重建稿与章节召回诊断 |
| 结论归属 | 需真机验收 | 见 [离线语料准确度](offline-accuracy.md) | 仅用于回归，不作为准确度结论 |

**为什么要有离线校核**：真机实测中麦克风外放收音的 RMS 常在 0.003~0.026（接近底噪）
而被门控挡掉，此时比对结果反映的是**收音**而不是算法。
离线路径把「抓音」与「模型实际转写」分开验证。

### 转写稿口径（关键）

- **离线校核**的转写稿是**模型实际 CTC 输出**：暂停切段互不重叠；
  超过 30 s 的无停顿段才用带时间戳的重叠窗口拼接。
  转写器只接收音频、模型输出和词表，**不查询期望章节或参考原文**。
- **流式诊断**的「转写稿」是**稳定命中章节的标准经文重建稿**，不是逐词 ASR。
  它保留用于分析章节误匹配、稳定事件和窗口推进；其 F1 的 hypothesis 是标准经文，
  与前者的实际 ASR 输出**不能直接比较**。

> 流式链路曾因窗口重复覆盖把 47 词语料累积成 150 个原始输出词、126 词语料累积成 1258 词，
> 这是改用章节重建稿的原因，也是「逐词 ASR 输出不能直接当长音频转写」的直接教训。

## 4. 流式会话参数

`QuranStreamingSession`（`lib/quran_offline/quran_recognizer.dart`）的默认配置：

| 参数 | 默认 | 作用 |
|------|------|------|
| `triggerSeconds` | 0.75 | 每累积约 0.75 s 尝试一次识别 |
| `minWindowSeconds` / `maxWindowSeconds` | 1.2 / 15 | 太短的窗口不识别；识别时只取最近 15 s |
| `silenceRmsThreshold` / `finalSilenceSeconds` | 0.012 / 1.5 | 连续静音 1.5 s 判定一段诵读结束 |
| `stableRounds` | 2 | 连续多轮命中同一章节才标记「稳定」，避免逐帧抖动 |
| `speechSnrRatio` | 2.5 | 音频内信噪比判据 |
| `speechQuietFloorRatio` | 2.0 | 会话级最安静本底倍数判据 |
| `speechRmsThreshold` | 0.004 | 极低电平兜底 |
| `assumeSpeech` | false | 灌音会话按「已知是朗读」建，跳过信噪比判据 |
| `topK` / `maxSpan` / `spanPenalty` | 64 / 4 / 0.1 | 召回候选数、最大跨度、跨度惩罚（`QuranMatcher` 默认值） |
| `commitWordRatio` | 0.6 | 稳定命中且已读词达该比例时提交一节到已确认序列 |
| `advanceWindowOnCommit` / `windowOverlapSeconds` | true / 1.0 | 提交后裁掉窗口前部音频，保留 1 s 重叠 |

> 广播侧使用**自己的一套配置**（`BroadcastMatchConfig`，`topK = 32`、`maxSpan = 8`），
> 因为两个库的 token 表与候选规模不同，阈值不可互相沿用。

词级进度：对候选序列做**帧级强制对齐**（`CtcScorer.alignFrames`），
把被 CTC 挤到音频内容区之后的 token 判为「尚未念到」，取前缀词数即已读词数；
序列帧数不足时回退到「前缀 CTC 打分 + 容差」（`defaultTolerance = 0.35`）。

## 5. 语料验证页

默认链路：**选中语料 → 按声学暂停分段 → 模型实际 CTC 转写 → 与预先冻结的原文逐词比对**。

| 语料来源 | 位置 | 说明 |
|----------|------|------|
| 内置语料 | `assets/quran_offline/corpus/`（由 `manifest.json` 描述） | `download_corpus.sh` 从 Quran.com CDN 取逐节诵读并拼成 16 kHz 单声道 WAV；清单用 `includesBismillah` 预先声明音频是否含太斯米，评测不按预测结果择优；**音频不入版本库** |
| 设备语料 | 应用私有目录 `files/corpus/*.wav` | 可有同名 `.txt` 作为原文；无 txt 时按文件名 `corpus_SSS_AAA_BBB.wav` 的章节区间取经文库原文 |

默认三段内置语料：

| 语料 | 节数 | 原文词数 | 时长 |
|------|------|----------|------|
| `36:1-5` | 5 | 12 | 28 s |
| `55:1-13` | 13 | 43 | 87 s |
| `67:1-11` | 11 | 122 | 159 s |

用法：

1. AppBar「语料验证」→ 语料列表（内置 + 设备自定义），默认打开「离线校核」；
2. 点一条即开始；跑完**自动进入「原文 / 转写」比对页**，返回列表后保留 F1 与结论；
3. 右上角「全部跑一遍」批量校核，逐条要求容错 F1、准确率、覆盖率均 ≥ 0.9，日志同时单列严格 WER；
4. 关闭「离线校核」后再运行，才进入实时节奏灌音链路并显示章节召回诊断。

设备语料的推送方法见 [Android 平台说明 §6.1](platform-android.md#61-自定义语料16-khz--单声道--16-bit-pcm-wav)。

## 6. 编译期开关

| 开关 | 默认 | 说明 |
|------|------|------|
| `_showTeleprompter` | `false` | `false` = 整句经文；`true` = 逐词提词器（已读 / 当前 / 未读三态高亮 + 自动居中滚动） |
| `quran_auto_start` | `false` | 内置样本验证结束后自动开麦 |
| `quran_auto_stop_seconds` | `0` | 自动开始后多少秒自动停止并输出 `比对预览` |
| `quran_auto_corpus` | `false` | 加载完成后自动进入语料验证并跑一遍全部语料 |
| `quran_headless_corpus` | `false` | 无界面验收入口（`OFFLINE_RESULT` / `OFFLINE_COMPLETE`） |

三个联调开关走 `--dart-define` 而非改源码，避免把联调状态误提交。
Android 的 `input tap` 被系统禁用、iOS 模拟器无法脚本点击，
因此无人值守验证只能靠它们（详见 [Android 平台说明 §3](platform-android.md#3-系统限制与替代手段)）。

## 7. 流式链路上踩过的两个坑（已修，保留回归）

1. **能量门控会整段挡掉连续朗读**：语料帧能量的峰值/中位数只有 1.3~2.0，
   低于 `speechSnrRatio = 2.5`（症状：灌音 0 事件、转写 0 词、F1 全 0）。
   处理：灌音会话按「已知是朗读」建（`assumeSpeech: true`），实时采集路径仍用完整门控。
2. **窗口推进在错误匹配下会裁掉真内容**：实测 159 s 语料被前移掉 155 s，越错越多。
   处理：只在冠军是**已确认序列的延续**（同节 / 往后 1~3 节 / 下一章开头）时才推进，
   且单次最多裁掉窗口的 60%。

## 8. 与上游 Tilawa 的受控对比

同一批语料（`assets/quran_offline/corpus/*.wav`）、同一份资产、
**同一套指标代码**（本项目的 `WordAlignment`）下，与 Tilawa 官方 npm 包
（`@tilawa/core`，默认配置）的实测对比：

| 语料 | Tilawa 章节命中 / F1 | 本项目章节命中 / F1 | 结论 |
|------|---------------------|---------------------|------|
| `36:1-5`（28 s） | 5/5，F1 **1.000** | 5/5，F1 0.744 | Tilawa 在短句连读上更干净且更快 |
| `55:1-13`（87 s） | **0/13**，F1 0.119 | 13/13，F1 **0.861** | 本项目在连读多节上明显更好（Tilawa 锁错章） |
| `67:1-11`（159 s） | 11/11，F1 **0.783** | 7/11，F1 0.752 | 基本持平 |

复现：

```bash
# Tilawa 侧（Node）：需要同一份 vocab / quran_ctc_tokens / quran.json 与改造版模型
cd tools/tilawa_compare && npm install
OUT=/tmp/tilawa_bench.json node run_bench.mjs

# 统一口径对比（两侧都用本项目的指标实现）
dart run tool/tilawa_compare_metrics.dart /tmp/tilawa_bench.json /tmp/ours_bench.json
```

> 口径提醒：该对比使用的是**章节重建稿**（流式链路），与离线实际 ASR 的 F1 不是同一口径；
> 两侧章节命中各自按其输出序列统计，平台也不同（Tilawa 在 Mac x86，本项目在真机 arm64）。

## 9. 一次失败的尝试（已全部回滚，留作教训）

为压掉流式链路里的「多余词」而试过四处改动：
**片段候选**（词边界上的前缀/中段）+ **内容帧短缺惩罚** + **信任门控** + **序列先验**。

真机跑批结果是**净负收益**：`55:1-13` 覆盖率从 0.926 掉到 0.649、F1 从 0.861 掉到 0.520；
同一轮批量汇总的章节命中从 25/29 降到 21/29。四处改动已全部回滚。

原因（也是后续改动应当避免的坑）：

1. **「解释内容帧比例」抓不住真正的多报**：多报的候选在**它自己的窗口**里解释比例往往很高，
   因为那段音频确实就是那句经文——问题出在**文本歧义**（同一段音频对应多节），
   不是「候选解释不了音频」。信任门控在三轮里只丢弃了 0~3 次，基本没起作用。
2. **片段候选在真实音频上反而抢走正确候选的冠军**：合成证据里「完整候选声学近乎完美」，
   真实音频不是——片段候选把 token 放在概率最高的少数帧、其余按空白摊掉，
   每帧平均因此可能高于正确但更长的完整候选。
3. **序列先验会放大一次误匹配**：无条件先验把一次错误匹配当成「延续」继续强化，
   越滚越偏。

结论：**合成证据能验证逻辑，但不能替代真实音频上的效果判断**；
改动匹配策略必须用真实音频跑批，并且要看「覆盖率 / 章节命中」而不是只看多余词数量。

## 10. 未定量评估的部分

- **提词器精度**：已读词估算已改为帧级强制对齐（不依赖容差常数），
  但高亮「滞后 / 超前」的量还没有按真人朗读实测；默认主区走整句样式，
  提词器逻辑保留且有单元测试覆盖；
- **实时路径的长诵风险**：VAD 的音频内信噪比判据（峰值 ≥ 中位数 × 2.5）
  隐含「窗口里既有朗读也有停顿」的前提，真人一口气不停顿地长诵时存在被挡风险
  （未做该场景的真人实测）；
- **短句误匹配**：短窗口上引擎会稳定地误认成别的短句
  （实测 `2:1`「الم」、`1:3`「الرحمن الرحيم」反复出现），
  它们进转写稿后成为多余词。根因是片段/前缀匹配的缺失（上游 Tilawa 有
  `JOINT_FRAGMENT_BLEND`、`JOINT_PREFIX_*` 那套处理），尚未移植。
