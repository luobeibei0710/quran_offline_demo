# 三栏实时同步与低延迟方案

## 目标与口径

广播首页的三栏分别显示实际 ASR 转写、全经候选原文和目标语言译文。预览属于正在收音的同一音频片段，终稿仍由静音或最长时长切分后完整复核并落库。预览经文一律标为候选；未匹配时不得猜测经文，机器翻译不得标为校订译本。

“同步”指每次展示的转写、候选和译文有相同的片段身份及候选版本；译文暂未完成时显示等待状态，而不是沿用上一候选的译文。“低延迟”指从音频到界面实际可见的时间，不能用单次匹配函数耗时替代。

## 当前基线

改动前的 `BroadcastSessionController._maybePreview` 在音频累计达到 1 秒且模型空闲时，对当前全部待确认音频重新转写、匹配，再一次性发布草稿与候选；同一候选连续两次出现后生成预览译文。`_processFinal` 对完整片段复核并保存。预览与终稿共享单模型。

2026-09-21 Android 旧版真机记录：预览匹配 P50/P95 为 615/1696 ms（n=635）；片段结束至终稿落库 P50/P95 为 4062/5733 ms（n=42）。这不是音频到三栏可见的端到端延迟，iOS 广播链路也尚未完成真机验收。详见 [真机验收记录](device-verification.md#35-性能)。

2026-09-23 新版 Android 局部试播第 12 章约 452 秒：转写与候选同帧可见的“最新音频块进入控制器→UI 帧”P50/P95 为 647/972 ms（n=384）；候选稳定后译文可见的额外 P50/P95 为 21/28 ms（n=151）。16 段终稿中 15 段指向第 12 章、1 段未匹配。两组时延口径与旧版数据不同，不能直接算改善百分比；全章准确率与真正端到端译文时延仍未验收。详见 [本轮实测证据](evidence/live-three-column-android-2026-09-23.md)。

## 实施设计

1. **有界预览音频**：`previewWindowSeconds` 默认 12 秒。预览只处理当前片段最近 12 秒，只做一次模型前向，同一份证据用于转写与匹配；终稿继续处理完整片段，不改变落库文本和匹配口径。预览窗口是及时反馈，不代表整句最终内容。
2. **同源版本**：每份预览记录会话代数、片段起点、窗口起止、预览序号、候选代数和候选键。转写与候选来自同一次推理。异步译文返回时，只有这些身份和目标语言仍对应当前候选才可写入；否则丢弃旧结果。候选稳定按经文引用判断，译文复用按节内词范围一起判断。
3. **来源准确**：预览翻译返回译文文本、`curatedEdition` / `machineCanonical` 来源和输入范围。已授权译本显示校订译本及整节上下文标记；机器翻译维持独立标签。未匹配预览不翻译波动的转写，终稿仍按原策略翻译实际 ASR。
4. **终稿优先**：单一推理工作泵先处理终稿队列，预览请求只合并为最新一份；预览在推理期间遇到断句时不得覆盖新片段。正式翻译的并发 `drain` 调用复用同一任务，避免重复执行。
5. **可观测延迟**：`[BroadcastLatency]` 日志记录末块音频进入控制器到草稿/候选 UI 首帧，以及候选稳定到译文 UI 首帧；普通预览日志保留窗口长度、匹配耗时和整轮处理耗时。新版 Android 局部试播已采集这两项 P50/P95，完整端到端译文时延和人工准确率仍须继续验收。主机合成测试不能证明真机达到时延目标。
6. **分段与退出**：最长时长强切保留的重叠音频不单独触发下一片段预览；新采样达到预览间隔后才恢复。服务退出先停止收音并等待推理、待办翻译及预览译文完成，再关闭模型、翻译引擎和数据库。仅供预览使用的内存译文缓存在会话结束时清理。

## 验收

- 自动化：未到终稿时草稿与候选可见；候选稳定后译文可见；候选/片段变化后旧译文不再出现；终稿到来时不丢队列；强切重叠音频不覆盖已确认内容；译本读取失败可退出等待态；退出会话等待在途推理、译文缓存写入与末句落库；权限申请期间退出不会重新启动音源；校订译本与机翻来源正确；长片段预览有界而终稿仍完整。
- 真机：逐次采集“音频终点→草稿/候选可见”“候选稳定→译文可见”“断句→终稿可见”的 P50/P95；在长段、短节、重复节、跳章、库外讲话和噪声场景人工核对经文位置与译文对应关系。分别报告 Android 与 iOS，不以转写与候选的一致性 F1 代替独立节号准确率。

建议将预览“最新音频进入→转写与候选共同可见”的 P95 ≤ 1.2 秒、热缓存校订译文在候选稳定后的额外 P95 ≤ 0.15 秒、三栏错配 0 次作为**真机标定目标**。Android 的前两项在本次约 452 秒局部试播中达到，但尚未经 30 分钟和多场景复验；三栏错配需要逐帧人工核对。终稿第一阶段要求 P95 不高于旧版 5.733 秒，但本次终稿日志口径不同，不能据此判定达标。

### 端到端时延的口径（2026-09-23 第二轮修订）

上面两项**不能相加**，也不能当作“语音进入麦克风到正确译文可见”的时延：译文要等同一候选连续
两轮稳定，且第二项只统计最终显示成功的那些版本。代码里已经埋了一条可关联的事件链
（`BroadcastLatencyTrace`，默认关闭，用 `--dart-define=quran_latency_trace=true` 开启）：

| 事件 | 含义 |
| --- | --- |
| `previewPublished` | 预览结果生成，带音频采样区间 `aStart/aEnd` 与 `aRecvUs` |
| `previewFrame` | 该预览首次真正绘制到界面 |
| `translationPublished` / `translationFrame` | 预览译文生成 / 带译文的预览首次绘制 |
| `translationDropped` | 译文在到达前被候选切换清掉（`pending` / `shown`） |
| `finalPublished` | 终稿落库，带片段起始与结束采样 |

建议口径：起点取该译文所属候选首次出现时的 `aStart`（用采样索引换算的会话内音频位置），
终点取对应的 `translationFrame.atUs`；“等待或被取消”的比例为
`translationDropped / (translationFrame + translationDropped)`。

**这三项都还没有真机样本**：现有 647/972 ms（n=384）与 21/28 ms（n=151）仍是上一轮那 452 秒
的两个分段指标，端到端 P50/P95、冷／热路径与取消比例必须重新测量后才能写进本文件。
详见 [第二轮验证证据](evidence/codebuddy-three-column-followup-2026-09-23.md) 第 5 节。

### 候选稳定性的已知量化结果（不是准确率）

同一 452 秒日志的机器可算统计（脚本 `tool/analyze_preview_evidence.py`）：跨章候选预览
145/383（37.9%），其中**连续两轮相同的跨章候选 33 对（占相邻预览对 8.6%）**——按现有策略
这类候选会触发预览译文，是最需要人工标注关注的一类；末次预览与终稿经文范围重叠
10/15（66.7%），但该口径以终稿为参考、混合了终稿自身的不确定度，不等同于标注样本上的
正确率。因此在拿到人工标注之前，**不得据此调整 `quran_match_service.dart` 的全局阈值**。

## 回滚边界

若 12 秒窗口在人工标注样本中的候选重叠率不达标，可调大 `previewWindowSeconds`；仍不足时将预览调用恢复为原 `transcribe` 路径。终稿算法、数据库和历史记录无需迁移。低延迟预览不得改变短节、重复节和太斯米的拒识规则。
